## Implemented

### Health

- Sleep context projection unions overlapping/touching explicit asleep intervals across stages and sources. Gaps remain gaps. Derived intervals carry `DERIVED` provenance, algorithm version, source IDs, and an explicit non-nightly-total limitation. Raw source observations are unchanged. This is interval-union accounting, not an assertion that contradictory devices agree about sleep.
- Android duplicate stage starts retain the longest explicit asleep interval when merged; awake/in-bed/unknown stages do not become sleep minutes. Stages outside session bounds fail the metric batch. Missing stages do not manufacture a session-duration measurement.
- HRV identities and labels separate SDNN, RMSSD, and unknown methods. Existing legacy HRV IDs are retained on reread/correction instead of creating duplicate imported records.
- Unchanged rereads retain first availability. Corrections retain first import time; older availability cannot overwrite a newer correction. Timezone-offset corrections are not ignored. Health provenance no longer substitutes the phone's current IANA timezone for an unavailable source timezone. Context dates use recorded offsets when present, otherwise device-local date.
- iOS/Android metric batches discard partial rows after an SDK/page/normalization error. Repeated Android page tokens terminate with a failed metric, and missing external IDs fail closed.
- Sync accepts only completed requested metrics and matching observations. Invalid/future date checkpoints fall back to the existing seven-day window. A failed metric does not replace records or advance its checkpoint. Disconnect/reconnect invalidation remains in place.
- Empty reads are deliberately not interpreted as deletions: HealthKit read access may be undisclosed, and missing records are not an authoritative deletion feed.
- Native sources now use explicit change feeds: HealthKit per-metric anchored queries with a fixed original lower-bound predicate, and Health Connect per-record-type change tokens. Pages are bounded at 20 per sync and each accepted page saves its observations, explicit deletions and next cursor together. More pages remain resumable with `health_more_changes_pending`; repeated nonempty tokens fail closed.
- Provider upserts carry source-parent IDs, and Health Connect retains actual `lastModifiedTime`. An explicit full parent update replaces only its own normalized sleep/heart-rate child set. Removed children produce `source_update` deletion records; provider deletion events produce `source_delete`. Matching requires platform, metric and exact parent identity. Legacy Android child IDs are recognized only with the exact parent plus ISO timestamp suffix.
- Health Connect bootstrap reserves the feed before reading a baseline, then consumes changes that occurred during the read. Expired tokens perform the same non-destructive bootstrap and persist `historyGap: true`; missing historical rows are never inferred deleted. Invalid HealthKit anchors/read failures retain the old cursor for retry, not an implicit destructive reset.
- Explicit seven-day resync validates source/metric/parent identity, accepts only upserts from its snapshot, and rejects a stale snapshot if another sync advanced that metric's cursor. The authoritative feed handles deletion afterward. Permission failure, malformed records and partial pages cannot advance their metric cursor.

### Device Persistence

- The existing partitioned Health store remains in place. A versioned write-ahead journal stores only the changed bucket writes and final device metadata before applying any of them. Reads replay a valid pending journal before exposing data; cursors cannot become visible without their associated source changes/deletions.
- Legacy optional fields can remain absent. Read-only legacy access makes no migration writes. The existing pre-partition backup is retained; no owner storage was opened or migrated during this work.
- Recovery validates journal keys/payloads before writing. Corrupt journals fail closed. Repository instances sharing one storage object serialize reads and updates. Crash injection at every transaction write verifies roll-forward recovery of rows, deletions and cursor together.
- Browser tabs/workers use one fixed origin-wide exclusive Web Lock around recovery and the latest read/update, including all bucket/metadata writes. Independent storage wrappers cannot bypass it through separate in-process queues. Unsupported browser contexts or rejected lock acquisition fail closed before touching storage; they never silently fall back to the WeakMap. Native execution retains its single-process storage-object queue.
- Tests simulate independent web contexts, lock contention, read isolation, interrupted-journal recovery and unavailable/rejected lock acquisition. They are deterministic lock-API fixtures, not a claim of live multi-tab acceptance. Independent native OS processes and direct writers bypassing the repository remain outside this guarantee. Standalone `HealthCollection.write` retains its old API; runtime source changes use `DeviceRepository`.

### Calendar

- Writes require an exact locally owned cached mapping, explicit confirmation, and a writable calendar. Stale confirmations fail rather than overriding later local edits.
- Native writes read back the OS event and verify its calendar, title, and event interval before mutation. Recurring/detached event writes fail explicitly because the current contract cannot safely express occurrence-specific mutations.
- Source IDs remain device-local; the adapter does not fabricate provider identity. Creates now retain platform attribution. Invalid/out-of-selection reads fail before replacing the cached calendar view.
- Concurrent explicit exports of the same block through one service instance reuse the mapping. In-flight reads cannot overwrite a later create/update/delete or a newer sync.
- Free events do not consume fixed schedule capacity. Busy and unknown events remain conservative constraints.
- Creates reject missing OS event IDs. A failed local commit now attempts journal recovery before compensating: a recovered successful mapping keeps its OS event; unreadable/uncertain local state returns `calendar_local_commit_retry_required` without deleting it. Only a confirmed absent mapping permits the existing just-created-event compensation. No incomplete Calendar queue or mapping interfaces were added.

### Notifications

- Native lock-screen title/body are always generic existing localized copy, even when a caller or stored snooze contains private text. Notification data contains routing identifiers, not health summaries.
- Disabled categories, deleted/completed blocks and missing skills cannot retain snoozes or accept reminder actions. Invalid daily times and corrupt snooze timestamps cannot crash/block valid planning.
- Follow-up scheduling and target/action validation reuse James's `markDecisionFollowUpDue(episode, now.toISOString(), data.executionLogs)`. They never trust a stored legacy Apply-timed `dueAt`. New real execution schedules without reopening the sheet; corrected endpoints move the horizon; deleted, ambiguous, unrelated, synthetic or closed episodes invalidate reminders. Revalidated due targets remain actionable. Snoozes cannot precede a corrected horizon; normal reconciliation cancels old invalid schedules. The original decision completion report's notification handoff is now implemented here.
- `notificationQuietHours?: { startMinute: number; endMinute: number }` is device-local. Integer endpoints are `0..1439`; equal endpoints/absence disable quiet hours. Malformed settings fail closed. Windows use local wall-clock time, include the start, exclude the end, and support same-day/overnight intervals. Non-block reminders defer to the quiet endpoint; accepted-block start reminders are suppressed rather than misleadingly delivered late. Daily OS triggers are adjusted too. DST tests include the repeated fall-back hour.
- The app records an intended notification ID before OS scheduling. Cancellations remove tracking only after success; failures retain IDs for retry. A request that completes after plan/session invalidation is cancelled.
- Foreground planning uses the current clock on every render and again when queued work actually runs. A bounded foreground minute tick refreshes day/deadline state without background polling. Reconciliation checks each request against a fresh clock, cleans expired requests without abandoning later ones, and rechecks after awaited permission/cancellation calls. Independent OS failures are reported after later requests have been attempted, with failed IDs retained for retry. Regression tests cover an expired 08:30 request followed by a valid 10:30 reminder and deadline crossings during awaited OS calls.
- OS reconciliation removes orphaned QuestLife schedules without touching unrelated IDs. Cancellation also dismisses delivered notifications.
- Auth/session changes invalidate queued plans immediately, clear pending in-memory intents, disable reminders, clear snoozes, cancel tracked schedules, and clear owned OS responses/delivered items. Foreground reconciliation retries failed cleanup. Startup uses the existing Sync V2 owner to detect retained local data after signout/account change; no new identity persistence was introduced.
- Response subscription waits for identity and device-data hydration. Late cold-start callbacks after unsubscribe are ignored; duplicate responses are suppressed across subscription recreation within the running process.
- Shortcut intents are excluded by a positive `isNotificationKind` guard before reminder-kind indexing. Both open-only `quick_capture` and `current_plan` are forwarded to the parent's intent route without reminder actions. `NotificationKind` and `NotificationRequest` were not enlarged by this slice.

## Remaining Integration and Device Gates

These are substantive remaining work, not claims that external credentials/hardware were probed and found absent.

1. **Parent integration acceptance: Health cloud deletions.** Dewey's runtime/engine handoff is now present with local tests. Parent must verify acknowledgement/retention, hydration versus pending deletion, and source-revision signatures at the final integration boundary. Same-account authenticated remote deletion/update convergence is not yet verified.
2. **Health history/OS limitation.** Expired Health Connect tokens cannot reconstruct already-lost deletion history from an empty baseline; `historyGap` remains explicit. Invalid HealthKit anchors fail closed and require a separately designed explicit recovery action rather than resetting on an indistinguishable permission/read error. No claim of complete historical reconstruction is made.
3. **Remaining code: durable Calendar export registry and operation queue.** `ownedIds` alone is not ownership; an exact owned cached event is required. `disconnect()` clears that cache, and range replacement can remove mappings, so later exports may create a second OS event. The in-memory export queue only serializes calls in one service lifetime. OS create success followed by process death before the local journal is written can orphan an event; update/delete success before local intent persistence can likewise leave stale local state. The new journal-aware compensation fix only closes failures after the local transaction has become durable. There is no durable confirmed-intent queue, native idempotency marker/reconciliation, retained export mapping, recurrence-instance write contract, provider-stable identity, or remote-to-device execution status. No partial interfaces for these were added. A next slice needs coordinated optional `calendar.pendingOperations`/`calendar.exportMappings` fields, explicit retry/reconciliation, and parent-owned cross-device intent/UI integration. Calendar IDs must remain local, not masquerade as portable provider IDs.
4. **Remaining notification integration/validation.** Parent owns token retirement, late/in-flight remote push behavior and Settings integration. Exactly-once domain actions across process death are not provided by the bounded in-memory response cache. Native payload privacy is generic for schedules created by this driver; remote sender privacy and device-displayed pushes require the parent boundary plus actual delivery validation.
5. **AWAITING_OWNER / VERIFIED_DEVICE not attempted.** An appropriately signed build, physical iPhone/Android, normal user-granted Health/Calendar/notification permissions and actual source records are required. Validate nonempty reads, re-read/correction/deletion, revocation, owned Calendar writes, lock-screen privacy, quiet hours, DST/timezone changes, cold starts, signout/relaunch and cleanup retry. Do not automate consent or write sample owner observations. Empty reads are not proof of zero activity or permission denial.
6. **VERIFIED_REMOTE not attempted.** Actual authenticated push delivery/token retirement, separately consented Health convergence and cross-device Calendar-intent execution remain unverified. No deployed-web end-to-end claim is made; this task forbids deployment and changes no UI surface.
