# Native foundation architecture

## Boundary

One Git repository and one domain/Store model. `App.web.tsx` retains the accepted
web entry. `App.tsx` resolves the native shell. Normal native navigation does not
read query parameters. `EXPO_PUBLIC_NATIVE_CHART_QA=true` is an explicit
`__DEV__`-only renderer fixture, outside Store and outside ordinary navigation.

Today remains `HomeScreen` orchestration with `.native.tsx` material, control,
sheet and surface adapters. Its ordering, command authority and parse/confirm
handlers remain shared. Notifications enter the existing Start, Finish, Direct
Log, State and History handlers. DONE opens actual-result confirmation; it never
manufactures a completed observation. SKIP requires an in-app confirmation.

`nativeFoundation.ts` maps Environment, Material, Text, Border, Interaction,
Semantic and Data from `visualFoundation.ts`. No independent screen palette.
Web CSS imports resolve through `.styles.web.ts`; native uses neutral sidecars.
The static portability inventory is triage, not device certification.

## Native modules and reproducibility

- Expo 54.0.37, React Native 0.81.5, React 19.1; New Architecture enabled.
- IDs: `com.kyrie.questlife` on both platforms. Existing history had no conflicting
  native identifiers. Local build numbers start at 1; EAS uses remote versioning.
- Android minimum API 26 (Android 8.0), required by Health Connect's library.
  Actual provider availability is checked independently before connecting.
- Expo-compatible dev-client, calendar, notifications, blur, gradients, linking,
  system UI and date/time controls. `react-native-webview` is pinned to 13.15.0.
- Native directories are generated by Expo prebuild and ignored. The Health
  Connect permission-delegate modification lives in a repeatable config plugin,
  not an untracked manual MainActivity patch.
- Android excludes HealthKit and its iOS-only Nitro runtime via Expo autolinking
  and RN configuration. The Android reader uses Health Connect independently.
- No remote EAS project identifier, certificate or account token is invented.

## Health module choice

Selected `@kingstinct/react-native-healthkit@15.1.0`, with
`react-native-nitro-modules@0.35.0` on iOS. Its published package declares RN
>=0.79 / React >=19 and tests against RN 0.81.5. It ships its Expo plugin, generated
New Architecture bindings and typed quantity/category/workout queries. This
matches this repository more closely than an old-architecture-only bridge.
A custom native module would duplicate permission/query plumbing and maintenance.
This is a source/compatibility decision, **not** proof of an iOS compile.

Android uses `react-native-health-connect@4.1.3`, its Expo plugin, typed record
queries and New Architecture codegen. The extra QuestLife config plugin registers
the permission callback and routes the OS permissions-rationale intent into
Settings. No background/history-expansion permission is requested.

## Health data contract and limitations

`HealthObservationV1` stores value/unit, event start/end, first available time,
source platform/app/device, external ID, recording method, timezone offset where
provided, Real Data Foundation provenance and limitations. Missing is not zero.
Eight readers: sleep, steps, heart rate, resting heart rate, HRV, exercise,
active energy and distance. No clinical records and no writes to Health APIs.

Sleep rows are explicit asleep intervals, not fabricated nightly totals.
HRV SDNN and RMSSD retain different construct labels. Source metadata that the
bridge does not expose remains unknown. Overlapping device/source observations
are preserved, not silently summed or claimed to be deduplicated measurements.

`HealthSync` performs a seven-day initial import, then a one-day overlap around
the saved cursor. Re-reading the same source ID replaces corrections, preserves
unchanged first-available time and never duplicates it. Cursor advances only on
a complete requested read; partial/failed reads retain retry state. Disconnect
invalidates in-flight reads and preserves already imported local records.

Source records live in a separate versioned AsyncStorage repository. The current
App ContextLog view is derived on demand through `healthContextView`, retaining
provenance. Existing Quant eligibility gates remain authoritative. Unsupported
interval/construct labels are excluded instead of renamed into a different
metric. This phase does not implement nightly sleep aggregation, cross-source
dedupe, HealthKit deletion anchors, Health Connect change tokens, full historical
import, background sync or encrypted/exportable source backup.

No private source content is placed in telemetry or console logs. Native analytics
are disabled by the platform adapter. The Insights refresh explicitly explains
the existing configured Quant-service data path. No source data is automatically
uploaded to third-party analytics. Source records are not mirrored to Supabase.

## Calendar

`CalendarService` owns permission checks, readable/writable calendars, bounded
reads, stable `calendarId + externalEventId` identity and explicit create/update/
delete. A persisted owned-ID registry gates writes. Spoofing a row's ownership
label cannot authorize writes. Failed local create removes only the event just
created by that operation. Disconnect invalidates stale readback.

The Schedule UI receives ephemeral externally owned fixed blocks; these never
become writable local ScheduleBlocks. `compileWithCalendar` feeds the same fixed
constraints to the existing compiler without changing its algorithms. Existing
Schedule does not expose a new automatic recompile workflow in this phase.
Explicit edits in native Calendar settings write through to the OS. There is no
general bidirectional schedule synchronization or automatic conflict resolver.

## Notifications and quick capture

One native NotificationService validates owned IDs, permissions, future times,
cancel/reschedule, response actions and optional future push token registration.
The planner uses accepted blocks, actual owner follow-up plans, chosen morning/
evening reminders and existing explicitly enabled skill reminders. Native global
notifications default off. The next 24 events are bounded; daily skill reminders
use OS daily recurrence. Removed IDs are cancelled; interrupted failures keep
persisted ownership for retry. This is not a remote push backend.

START/DONE/SKIP/OPEN route to existing app handlers. SNOOZE schedules ten minutes
later. Notification content deliberately omits private calendar/health details.
No first-launch permission prompts. Exact behavior still requires OS/device QA.

QuickCaptureSuggestionEngineV1 ranks at most three existing actions using current
accepted schedule, recurrence, hour-of-day recurrence, optional active-goal
context and recent use/capture history. Stable ID tie breaking. No LLM and no
prediction claim. Tapping creates the existing confirmation draft with **empty**
measured fields, not assumed duration/quality. Normal text parsing is unchanged.

## Chart

`QuestLifeChartModelV1` wraps existing chart presentation props. Web delegates to
the existing renderer; native serializes materialized points/candles/indicators/
references/events into a typed local WebView bridge. No OHLC, baseline or Quant
statistics are calculated inside it. Comparison, pan/pinch, crosshair, fit/zoom,
line/candle/bar and current-value markers use the installed chart library.

The library and license are bundled locally by `scripts/build-native-chart.mjs`.
CSP disables network access; navigation and file access are blocked. Attribution
is retained and About exposes the bundled license. The native screen selects
available artifacts and does not display fixture values in owner mode.

## Build and device prerequisites

Local development: `npm run android -- --device` or `npm run ios -- --device`.
Use the development client, not Expo Go. EAS profiles: development,
development-simulator, preview (internal APK) and production. Actual EAS project
linking/signing requires owner authentication and remains an explicit gate.

Native API calls require `EXPO_PUBLIC_API_ORIGIN` to be an explicitly configured
HTTPS service origin. An unset origin fails closed. Web same-origin APIs remain
unchanged. Existing local-to-Supabase mirror, explicit deletion outbox and retry
semantics are preserved; no hydrate, account system or two-way sync is added.

Local QA uses a new emulator and isolated browser profile with no API origin and
sync/analytics disabled. It must not write test observations to owner production.
Web/mobile viewport screenshots do not count as iPhone native screenshots.
