## Implemented

- Inspected the existing `questlife_sync_devices` columns: `user_id`, `device_id`, `platform`, `app_version`, `name`, `last_seen_at`, with `(user_id,device_id)` primary key and owner RLS. Added candidate migration `supabase/migrations/202609200002_device_push_boundary.sql` on that table, not a parallel registry.
- Registration, retirement, device metadata touch, manual-send claim and receipt completion are authenticated RPCs deriving the owner exclusively from `auth.uid()`. No UID parameter, service-role write, anonymous execute grant, direct authenticated token update, or token SELECT grant. Existing safe device listing remains readable under RLS. Unique active token/device bindings prevent A/B rebinding.
- Each registration has an opaque UUID, monotonic generation and 24-hour lease. Exact-generation retirement clears the token and retains a tombstone; delayed registration cannot resurrect it. Late provider responses cannot retire a newer binding. Reconciliation renews after one hour when invoked.
- `src/sync-v2/pushRegistry.ts` lazily uses the existing actual Supabase session, persisted Sync owner and existing `notificationsEnabled` preference. Network requests capture the original bearer rather than following a switched global SDK session. Public environment names remain `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY`.
- The new versioned journal uses existing session storage and stores only owner/device/generation, phase, token fingerprint and lease metadata. It never stores the Expo token or an additional bearer. Intent is durable before registration; ambiguous/lost ACKs retire rather than replay. Existing user records are not migrated.
- `authService.signOut()` retires the current device token before SDK local sign-out. Offline/failed retirement leaves both a durable pending intent and the A session; it throws instead of claiming logout. Existing runtime startup/foreground/retry ticks retry retirement and finish logout after acknowledgement. B cannot use A's journal/token or perform A's retry. A newly observed B session is never signed out by A's completed cleanup. Permanently lost A credentials require A reauthentication for cleanup; lease expiry prevents sends meanwhile but does not silently reassign ownership.
- `NativeSettingsScreen` explicitly passes the production `registerNativePushToken` callback. `NativeNotificationPreferences` also has that real default, not an unwired optional success path. The UI captures account identity before permission/token acquisition, disables registration while signed out or reminders are off, discards account-switch/logout responses, and reports registration only after an ACK. Permission denial and the reminder master switch retire the registration; failed retirement leaves reminders off and shows an error. Quiet-hours and other workers' screen changes are preserved.
- `POST /api/push-test` accepts only `{deviceId,requestId,action: 'send' | 'receipt'}`. It remotely verifies the Supabase bearer, then uses owner-bound RPCs. One own registered device per request, one new send per minute per device, durable duplicate suppression. Caller-provided recipient, UID, message or health content is rejected; request size is capped at 1024 UTF-8 bytes.
- Expo payload is fixed: QuestLife / `Open QuestLife.`, TTL 60 seconds, `data:{source:'questlife',kind:'push_test',registrationId}`. No health data, account ID, task ID or private text. The Supabase bearer never goes to Expo. Optional `EXPO_PUSH_ACCESS_TOKEN` is server-only. Tickets/receipts always return `delivered:false`; provider acceptance is not device-delivery proof. A lost provider ACK stays pending and cannot cause an automatic duplicate send. No hosted cron or paid service was added.
