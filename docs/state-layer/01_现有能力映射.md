## 1. StateCheckIn：字段、保存、同步、读取方

**结构**（`src/types.ts:683`）：`id / date / timestamp / timeBlock? / overall (必填 1–5) / energy? / focus? / mood? / physical? / stress? / label? / context?{sleepQuality, sick, postWorkout, …} / note? / dataProvenance? / createdAt / updatedAt?`

**保存**：
- `createStateCheckIn` / `updateStateCheckIn` / `deleteStateCheckIn`（`src/store.tsx:1109-1137`）。写入时整行展开（`...checkIn`），**不会丢掉未声明的字段**。
- 读盘迁移 `migrateStateCheckIn`（`src/storage.ts:177`）同样是 `...checkIn` 展开，旧数据补默认值，新字段原样保留。
- 持久化确认：`waitForLocalWrites()`（`src/store.tsx:66`），ACK 后 resolve、失败 reject；`retryLocalWrites()` 用于重试。

**同步**（SyncV2）：
- `stateCheckIns` 在 `APP_ENTITY_TYPES` 里（`src/sync-v2/contracts.ts:12`）。
- 校验 schema（`src/sync-v2/registry.ts:47`）只要求 `id / overall 1–5 / date / timestamp`，并且是 `.passthrough()`，**额外字段会原样上传和下发**。
- 限制：
  - 单条 payload ≤ 128 KB。
  - `contaminated()` 会拒绝带 `origin: SYNTHETIC|QA_TEST|DEBUG…`、`isFixture`、`trigger: 'debug'`、`fixture` 等字段的记录（`registry.ts:107-133`）。
  - id 不能含 `fixture|synthetic|qa|debug|demo` 片段。
- **结论：状态层的新字段放进 StateCheckIn 的一个子对象里即可同步，无需 migration。** 唯一硬约束是 `overall` 必填 1–5。

**读取方**（会受新签到影响的地方）：
- `todayCommand.isLowState`（`src/utils/todayCommand.ts:79`）：`energy ≤ 2` 或 `focus ≤ 2` 或 `overall ≤ 2` 时，Today 主动作变为 `rescue`（「2 分钟最低动作」）。**状态层写入的 `energy` 会直接影响 Today 主动作，这是期望行为**（todayCommand 仍是权威）。
- `HomeScreen` 的状态摘要 / 状态 sheet（`src/screens/HomeScreen.tsx:741-800, 1412-1442, 1696`）。
- `adaptive-decision/contextAssembler.ts:400`、`utils/decisionPayload.ts:211/241/501`（AI 决策上下文，读 stress/energy）。
- `insights-v3` 的 `state_stress` 仪表（`insightsV3Presentation.ts:70`）。
- **现有 `stress` 没有界面说明方向**，只有标签「压力」，默认值 3。状态层把「紧绷 1–5（很松…很紧）」映射到 `stress`，方向与「压力」一致（大 = 更紧）。

## 2. ScheduleBlock、planPatch、DecisionEpisode、回访

**ScheduleBlock**（`src/types.ts:261`）：`id / title / date / startTime / endTime / plannedMinutes / taskType / flexibility (fixed|flexible|movable) / rigidity / status / placementLocked? / linked* / notes? / source?`
- 同步 schema（`registry.ts:66`）同为 `.passthrough()`，**加可选 `demand` 字段可以原样同步**。
- 现有 `taskType`（deep_study / light_review / strength_training / cardio_recovery / admin / life_maintenance / creative_building）可以作为 `demand` 的默认推断来源。

**planPatch**（`src/adaptive-decision/planPatch.ts`）：
- `createDecisionPlanPatch({before, after})` 生成逐块 add/update/remove 操作，**fixed 块变动直接抛错**。
- `applyDecisionPlanPatch` 先校验「预览后块没被改过」，再校验最终放置不冲突。
- `undoDecisionPlanPatch` 反向回滚，同样有冲突校验。
- 状态层的「重排今天」只要产出 `after` 快照，就能复用整条链路的冲突检测和撤销。

**DecisionEpisode**（`src/adaptive-decision/decisionEpisode.ts`）：
- 状态机：DRAFT → … → PROPOSED → ACCEPTED → APPLIED → FOLLOW_UP_DUE → OUTCOME_RECORDED → CLOSED（`decisionEpisode.ts:368`）。
- 保存在 `DecisionResult.decisionEpisode` 里（`types.ts:883`），随 `decisionResults` 同步。同步 schema 要求 `mode / headlineInsight / createdAt`。
- 引擎：
  - `selectDecisionAction` → `applyAcceptedDecision`（确认后才 apply，写 `appliedPlanPatch`，`undoState.available = true`）→ `undoAppliedDecision`（`decisionEngine.ts:287-372`）。
  - Owner 的撤销额外检查「改动的块已有执行记录」和「已开始/已过期的块」，这两种情况不允许撤销。
- Store：`createDecisionResult`、`updateDecisionEpisode`、`applyDecisionSchedulePatch`、`undoDecisionSchedulePatch`（`store.tsx:1460-1515`）。

**回访**（`followUp.ts`）：
- `followUpDueAt` 支持 two_hours / end_of_day / next_morning。
- `dueOwnerDecisionEpisode` 找到到期的 episode（`ownerDecisionFlow.ts:126`）。
- Today 上有「回访」入口（`HomeScreen.tsx:2359-2367`），但它挂在 `questlife_core_v1` 开关后面，**Web 默认关闭**（`adaptive-decision/featureFlag.ts:8`，原生默认开）。

**入口**：
- `QuestLifeCoreOwnerSheet` / `AdaptiveDecisionLoopOwnerSheet`（`HomeScreen.tsx:3208-3230`），由 Today 工具行进入。
- Web 默认看不到这两个入口（需要 `?questlife_core_v1=1` 或 `?adaptive_decision_loop=1`）。

## 3. Health 数据在 Web 上能拿到什么

- Web 的 `HealthSource`（`src/platform/health/HealthSource.ts`）恒为 `isAvailable: false`，限制码 `NATIVE_REQUIRED`。**Web 自己读不到任何 Health 数据。**
- 但 `healthObservations`（sleep / resting_heart_rate / hrv / steps / exercise …）是 SyncV2 实体类型（`contracts.ts:20`、`sync-v2/runtime.ts:62-171`）。**如果用户在 iPhone 上导入过 HealthKit 并登录同步，Web 会收到这些观测值**，存在 `deviceRepository`（`src/platform/deviceRepository.ts`，`useDeviceData()` 读取）。
- 手动睡眠：
  - `ContextLog{type:'sleep', unit:'min'}`，可能来自手动输入或 `healthContextParser` 从文本里解析（`utils/healthContextParser.ts:172`）。
  - 首用写的是 `ContextLog{type:'sleep', unit:'睡眠自评1-3'}`，**单位不同，不能当分钟用**。
- **降级方案**（写进状态模型）：
  1. 睡眠分钟数优先取 `healthObservations(metric=sleep)`，其次取 `ContextLog(type=sleep, unit=min)`。两者都没有就记为「没用到睡眠」，在理由行写明。
  2. 静息心率 / HRV 只有来自同步的观测值才用，Web 本地没有就跳过，并在理由行写明「没有心率数据」。
  3. 睡眠自评（1–3）只用作「睡得差」的弱信号，单独标注，不与分钟混用。

## 4. 日历占用怎么进入

- Web：`useExternalCalendarBlocks` 恒返回 `[]`（`src/platform/calendar/useExternalCalendarBlocks.ts`），**Web 上没有外部日历**。
- 原生：`useExternalCalendarBlocks.native.ts` + `CalendarService`，外部事件以只读 `ExternalCommitment` 形式进入 `deviceRepository.calendar.events`。
- 应用内日程 = `data.scheduleBlocks`（用户手建 + 技能规则生成）。
- **状态层的「今天日历占用小时数」= 今天剩余的 scheduleBlocks 时长（Web）**，原生上再加上外部事件。缺失时不计入理由。

## 5. Capture 的自然语言解析能否复用为「清空脑子」

- 解析走 `/api/parse`，必须登录（`src/services/authenticatedAi.ts:24`，`HomeSmartCapture.tsx:82`）。**云端 AI 默认关闭，本地没有后端，不能作为「清空脑子」的前提**（与首用决策 #11 同理）。
- **复用方式**：
  - 「清空脑子」用确定性的本地切分：按换行、「；」「，」「、」等拆成条目，用户逐条三选一。不依赖 AI。
  - 以后若登录且开了 AI，可以在列表生成后由 `/api/parse` 补「建议时间」，但默认不调用。
- 「结果写成真实记录」的落点：
  - **一条 `ContextLog{type:'custom', label:'清空脑子'}`**：`brainDump` 子对象保存每条的选择；ContextLog 同步 schema 也是 passthrough。
  - **「排时间」的条目以 `ScheduleBlock` 的 add 操作走 planPatch 预览 → 确认 → apply → 可撤销**，不直接写日程。
